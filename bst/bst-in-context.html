BSTs in Context:
Comparing Data Structures

Time complexity and memory trade-offs across vectors, linked lists, and binary search trees.

Data Structures at a Glance

A quick recap of the three structures before comparing them:

Vectors

Contiguous, resizable arrays. Elements are stored in adjacent memory locations. In C++: std::vector.

Linked Lists

Chains of nodes connected by pointers. Each node holds data and a link to its neighbor(s). In C++: std::list (doubly-linked).

Binary Search Trees

Hierarchical structure where each node has at most two children. All values in the left subtree are less than the node; all values in the right subtree are greater.

Operation Details

Vectors

Access by index: O(1). Elements are contiguous in memory, so any element is reachable via a single pointer offset — no traversal needed.

int element = vec[5];           // O(1) — direct address calculation

Insertion and deletion:

  • At the beginning or middle: O(n) — all subsequent elements must shift to fill the gap.
  • At the end: O(1) amortized — capacity doubles on reallocation, so the average cost per push is constant.
vec.push_back(value);              // O(1) amortized
vec.insert(vec.begin(), value);    // O(n) — shifts every element right

Search:

  • Unsorted: O(n) linear scan.
  • Sorted: O(log n) with std::lower_bound.
auto it = std::find(vec.begin(), vec.end(), value);        // O(n)
auto it = std::lower_bound(vec.begin(), vec.end(), value); // O(log n) — sorted only

Linked Lists

Access by index: O(n). No random access — must traverse from the head (or tail) one node at a time.

auto it = std::next(list.begin(), n);  // O(n) — traverses n links

Insertion and deletion:

  • At the beginning or end: O(1) with head/tail pointers.
  • At a known iterator position: O(1) pointer rewiring.
  • Finding that position first: O(n).
list.push_front(value);          // O(1)
list.push_back(value);           // O(1)
list.insert(pos_itr, value);     // O(1) once iterator is in hand

Search: O(n). Must traverse from the head with no shortcutting possible.

auto it = std::find(list.begin(), list.end(), value);  // O(n)

Binary Search Trees

All three core operations — search, insert, delete — are O(log n) average in a balanced tree and O(n) worst case in a degenerate (skewed) tree.

An in-order traversal visits all nodes in ascending sorted order in O(n) — producing sorted output without an additional sort step.

STL Containers Backed by BSTs

The C++ standard library implements std::map, std::set, std::multimap, and std::multiset as red-black trees — a self-balancing BST variant that guarantees O(log n) for all operations. See the next page in this module for usage examples.

Memory Locality and Cache Performance

Memory layout often matters more than raw size. Modern CPUs load data in cache lines — contiguous blocks fetched together. Structures that scatter nodes across the heap defeat this mechanism:

  • Vectors: Excellent cache performance. Iterating a vector is one of the fastest operations in practice because all data is contiguous and prefetched efficiently.
  • Linked Lists: Poor cache locality. Each node is a separate heap allocation, so every traversal step likely causes a cache miss.
  • BSTs: Also poor cache locality for the same reason — pointer-chasing walks unpredictably through memory.

This is why a sorted std::vector with binary search often outperforms a BST in practice despite both being O(log n) for search — the vector's cache behavior wins on real hardware.

Balanced vs. Unbalanced BSTs

The O(log n) guarantee only holds when the tree stays balanced. Inserting values in sorted order into a plain BST produces a degenerate tree — essentially a linked list — and all operations degrade to O(n).

⚠ Inserting 1, 2, 3, 4, 5 in order into an unbalanced BST produces a fully right-skewed tree of height n. Every operation becomes O(n).

Self-balancing variants restructure the tree automatically to maintain O(log n):

Operation Unbalanced BST (worst case) Balanced BST (AVL, Red-Black)
Search O(n) O(log n)
Insertion O(n) O(log n)
Deletion O(n) O(log n)

AVL trees and Red-Black trees will be covered in later modules.

Summary

Each structure has a clear niche:

  • Vectors — best for random access and cache-friendly iteration. Prefer when you mostly read data or append to the end.
  • Linked Lists — best for frequent insertion and deletion at known positions. Poor choice for search or random access.
  • BSTs — best when you need a dynamic, always-sorted collection with efficient search, insert, and delete. The trade-off is higher memory overhead and poor cache behavior compared to vectors.

As always, the right choice depends on your workload: which operations are most frequent, how large the data is, and whether cache performance matters for your use case.

Food for Thought: Lazy Deletion

Standard BST deletion is the most complex of the three core operations. What if we deferred the structural work?

Lazy Deletion

Instead of structurally removing a node, mark it as deleted with a boolean flag. The node stays in the tree. A later insertion of the same value can reuse the node by simply clearing the flag.

Consider the trade-offs for a lazy BST:

  • Deletion: O(log n) — locate the node and set a flag; no pointer rewiring needed.
  • Insertion: O(log n) — if the value already exists as a deleted node, reuse it; otherwise insert normally.
  • Search: O(log n) — must check the deleted flag at each visited node to filter out "gone" values.
  • Space: Deleted nodes remain in memory — the tree grows over time if deletions outpace reinsertions.
⚠ Lazy deletion trades time for space. If deleted nodes are never reinserted, memory usage grows without bound. A real implementation needs a periodic rebuild or a threshold that triggers cleanup.

Think about: What condition triggers a full rebuild? How do you decide when the cost of accumulated deleted nodes outweighs the savings from deferred deletion?
