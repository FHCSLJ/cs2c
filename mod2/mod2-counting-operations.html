Counting Operations Examples

From exact counts to Big O intuition in algorithm analysis.

What Is Algorithm Analysis?

Algorithm analysis is the process of evaluating the efficiency of an algorithm in terms of the time and space it requires as the input grows.

In this introduction, we focus primarily on time complexity, or how runtime grows as the input size increases. The goal is not to predict the exact number of clock cycles on a particular machine, but to build a useful model for comparing approaches.

That is why algorithm analysis helps us reason about questions like this without having to implement and benchmark every possible solution:

  • How does linear search behave as the input gets larger?
  • When is binary search a meaningfully better choice?
  • When is code optimization helpful, and when does the real win come from choosing a different algorithm?

Counting Operations

The first step in analyzing algorithms is counting the operations the computer must perform. That sounds simple, but it immediately raises a subtle question: what should count as one operation? The answer depends on the level of abstraction we choose.

Example 1: Print a Single Value

void print_value(int x)
{
    std::cout << x;
}

Operations count:

  • Print operation: 1 operation
  • Implicit return from the function: 1 operation

Total: 2 operations

Even a statement that feels simple, such as std::cout << x, hides internal work. As we move toward Big O notation, we will stop caring about every detail and focus more on growth rate than exact counts.

Example 2: Sum Two Numbers

int add(int a, int b)
{
    return a + b;
}

Operations count:

  • Addition: 1 operation
  • Return statement: 1 operation

Total: 2 operations

Exercise A

Count the number of operations in the following function:

int sum_three(int a, int b, int c)
{
    int temp = a + b;
    return temp + c;
}
Answer

This function performs several operations:

  • Addition: a + b (1 operation)
  • Assignment: temp = a + b (1 operation)
  • Addition: temp + c (1 operation)
  • Return statement: 1 operation

Total: 4 operations

As a learning exercise, it is useful to count everything. In practice, we often focus on the operations that dominate the running time or are most relevant to the problem domain.

Loops and Growth

The real power of algorithm analysis shows up once we start examining loops. Loops are where running time begins to scale with input size.

Example 3: Sum an Array

int sum_array(int arr[], int n)
{
    int sum = 0;
    for (int i = 0; i < n; i++)
    {
        sum += arr[i];
    }
    return sum;
}

Operations analysis:

  • Variable initialization: 2 operations
  • Loop condition checks: n + 1 operations
  • Loop counter increments: n operations
  • Array accesses: n operations
  • Addition and assignment: 2n operations
  • Return statement: 1 operation

Total: 5n + 4 operations

This is a good example of why exact counting is a stepping stone rather than the end goal. Once we see the linear pattern, the key idea becomes that this algorithm grows proportionally with n.

Exercise B

Count the operations in this function that finds the maximum value in an array:

int find_max(int arr[], int n)
{
    int max = arr[0];
    for (int i = 1; i < n; i++)
    {
        if (arr[i] > max)
        {
            max = arr[i];
        }
    }
    return max;
}
Answer

This function performs these operations:

  • Initial array access and assignment: 2 operations
  • Loop initialization: 1 operation
  • Loop condition checks: n operations
  • Loop counter increments: n - 1 operations
  • Array accesses in the conditional: n - 1 operations
  • Comparisons in the conditional: n - 1 operations
  • Array accesses in the body: up to n - 1 operations
  • Assignments in the body: up to n - 1 operations
  • Return statement: 1 operation

Worst case: if the array is in ascending order, every conditional succeeds, so the total is 6n - 1 operations.

Best case: if the first element is already the maximum, the body never executes, so the total is 4n + 1 operations.

Example 4: Print All Pairs

void print_pairs(int arr[], int n)
{
    for (int i = 0; i < n; i++)
    {
        for (int j = 0; j < n; j++)
        {
            std::cout << arr[i] << "," << arr[j] << std::endl;
        }
    }
}

Operations analysis:

  • Outer loop initialization: 1 operation
  • Outer loop condition checks: n + 1 operations
  • Outer loop increments: n operations
  • Inner loop initialization: n operations
  • Inner loop condition checks: n(n + 1) operations
  • Inner loop increments: n^2 operations
  • Array accesses: 2n^2 operations
  • Print operations: 4n^2 operations
  • Implicit return from the function: 1 operation

Total: 8n^2 + 4n + 3 operations

In Big O notation, this becomes O(n^2) because the quadratic term is what dominates as n grows.

Exercise C

Count the operations in this function that checks whether an array contains duplicate values. This example is intentionally messier, because realistic counts can be much harder to pin down exactly than the earlier examples suggest.

bool has_duplicates(int arr[], int n)
{
    for (int i = 0; i < n; i++)
    {
        for (int j = i + 1; j < n; j++)
        {
            if (arr[i] == arr[j])
            {
                return true;
            }
        }
    }
    return false;
}
Answer

This function performs these operations:

  • Outer loop initialization: 1 operation
  • Outer loop condition checks: up to n + 1 operations
  • Outer loop increments: up to n operations
  • Inner loop initialization: up to 2n operations
  • Inner loop condition checks: up to (n^2 + n) / 2 operations
  • Inner loop increments: up to (n^2 - n) / 2 operations
  • Array accesses in the comparison: up to n^2 - n operations
  • Equality comparisons: up to (n^2 - n) / 2 operations
  • Return statement: 1 operation

Worst case: no duplicates are found, so we perform all iterations. The inner loop runs (n - 1) + (n - 2) + ... + 1 = n(n - 1) / 2 times, giving an approximate total of 5n^2 / 2 + 5n / 2 + 3 operations, which is O(n^2).

Best case: a duplicate is found immediately in the first comparison, so the work is constant, or O(1).

Big O Notation

Rather than counting exact operations forever, computer scientists use asymptotic notation, especially Big O notation, to describe how algorithms scale.

O(1)

Constant time, the work does not grow with the input size.

O(log n)

Logarithmic time, growth is very slow even as the input becomes large.

O(n)

Linear time, work grows in direct proportion to the input size.

O(n log n)

Linearithmic time, common in efficient comparison-based sorting algorithms.

O(n^2)

Quadratic time, often appears in nested-loop algorithms.

O(2^n)

Exponential time, growth becomes impractical very quickly.

Revisiting the earlier examples:

  • Print a value: O(1)
  • Sum two numbers: O(1)
  • Sum an array: O(n)
  • Print all pairs: O(n^2)

Code Optimization vs. Algorithm Selection

It is important to separate two different ideas. Code optimization improves constant factors without changing the overall scaling behavior. Algorithm selection changes the fundamental approach and can dramatically change how runtime grows.

Optimization Example

// Unoptimized
for (int i = 0; i < n; i++)
{
    for (int j = 0; j < n; j++)
    {
        result[i][j] = a[i][j] + b[i][j];
    }
}

// Optimized
for (int i = 0; i < n; i++)
{
    int* result_row = result[i];
    int* a_row = a[i];
    int* b_row = b[i];
    for (int j = 0; j < n; j++)
    {
        result_row[j] = a_row[j] + b_row[j];
    }
}

Approximate totals:

  • Unoptimized version: 10n^2 + 4n + 3 operations
  • Optimized version: 7n^2 + 10n + 3 operations

Both versions are still O(n^2). The optimization changes the constant factor, not the asymptotic growth rate.

Algorithm Selection Example

// Linear search - O(n)
bool linear_search(int arr[], int n, int target)
{
    for (int i = 0; i < n; i++)
    {
        if (arr[i] == target)
        {
            return true;
        }
    }
    return false;
}

// Binary search - O(log n)
bool binary_search(int arr[], int n, int target)
{
    int left = 0, right = n - 1;
    while (left <= right)
    {
        int mid = left + (right - left) / 2;
        if (arr[mid] == target)
        {
            return true;
        }
        if (arr[mid] < target)
        {
            left = mid + 1;
        }
        else
        {
            right = mid - 1;
        }
    }
    return false;
}

Worst-case totals:

  • Linear search: about 4n + 3 operations, or O(n)
  • Binary search: about 11 log2(n) + 4 operations, or O(log n)

For n = 1,000,000, that is the difference between roughly 4,000,003 operations and about 220 operations. That gap is why algorithm selection matters so much more than small optimizations when inputs become large.

Exercise D

Analyze the time complexity of these two functions that compute the sum of all elements in a 2D matrix:

// Approach 1
int sum_2d_array_1(int matrix[100][100], int n)
{
    int sum = 0;
    for (int i = 0; i < n; i++)
    {
        for (int j = 0; j < n; j++)
        {
            sum += matrix[i][j];
        }
    }
    return sum;
}

// Approach 2
int sum_2d_array_2(int matrix[100][100], int n)
{
    int sum = 0;
    for (int i = 0; i < n; i++)
    {
        int row_sum = 0;
        for (int j = 0; j < n; j++)
        {
            row_sum += matrix[i][j];
        }
        sum += row_sum;
    }
    return sum;
}
Answer

Approach 1: 6n^2 + 4n + 4 operations

Approach 2: 6n^2 + 7n + 4 operations

Both functions are O(n^2). The difference in exact counts is small compared with the dominant quadratic term. Approach 2 may perform better on real hardware due to cache behavior, but it does not change the asymptotic complexity.

Conclusion

Algorithm analysis is about understanding how performance scales with input size.

  • Code optimization can improve constant factors.
  • Algorithm selection can change the growth rate entirely.

For small inputs, both can matter. As inputs grow, choosing the right algorithm becomes far more important than trying to fine-tune an inherently inefficient one.
