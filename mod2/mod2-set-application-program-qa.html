Set Application Program Q&A

Test-driving Set<T> and understanding how the same class can act as both solver and solution.

The Main Question

A common point of confusion is what the Set<T> object is doing from the user’s point of view. The user owns the original collection of elements, creates a Set<T> that can reason about that collection, and then asks it to solve the subset sum problem.

Key idea: The same Set<T> class can appear in more than one role. One object can help search for the best subset, while another Set<T> object can represent the subset that was found.

That may feel unusual at first, but it is perfectly reasonable. A single class can be designed to both do work and represent results, provided its interface supports both jobs.

A Simple Test Drive

Here is a straightforward example that you could try from src/main.cpp in your project:

int main(int, char**)
{
    std::vector<int> all_the_things = {2, 5, 9, 4, 1};
    Set<int> set(&all_the_things);

    size_t target = 10;
    Set<int> best_set = set.find_biggest_subset_le(target);

    std::cout << "Sum: " << best_set.get_sum() << std::endl;
    std::cout << best_set << std::endl;
}

Expected output:

Sum: 10
{
 9
 1
}

This example shows the dual use of the class:

  • set is the object that knows how to solve the subset sum problem using the original collection.
  • best_set is the object that represents the subset returned as the answer.

Depending on how you implemented the class, the solver object may mainly reference the original collection while other Set<T> objects represent candidate subsets during the search. The important point is not the exact private layout, but that the public interface allows both roles to make sense.

Using Set<T> with a Custom Type

The subset sum machinery is more interesting once we remember that templates let us work with types other than int. If the type supports the operations your implementation expects, the same Set<T> design can work with user-defined objects too.

class Fancy_Class
{
private:
    int _value;
    std::string _name;

public:
    Fancy_Class(int value, std::string name = "") : _value(value), _name(name) {}

    int get_value() const { return _value; }
    std::string get_name() const { return _name; }
};

Fancy_Class operator+(const Fancy_Class& lhs, const Fancy_Class& rhs)
{
    int combined_value = lhs.get_value() + rhs.get_value();
    std::string combined_name = lhs.get_name() + " & " + rhs.get_name();
    return Fancy_Class(combined_value, combined_name);
}

int& operator+=(int& lhs, const Fancy_Class& rhs)
{
    lhs += rhs.get_value();
    return lhs;
}

size_t& operator+=(size_t& lhs, const Fancy_Class& rhs)
{
    lhs += rhs.get_value();
    return lhs;
}

bool operator<(const Fancy_Class& lhs, const Fancy_Class& rhs)
{
    return lhs.get_value() < rhs.get_value();
}

bool operator<=(const Fancy_Class& lhs, const Fancy_Class& rhs)
{
    return lhs.get_value() <= rhs.get_value();
}

bool operator>(const Fancy_Class& lhs, const Fancy_Class& rhs)
{
    return lhs.get_value() > rhs.get_value();
}

bool operator>=(const Fancy_Class& lhs, const Fancy_Class& rhs)
{
    return lhs.get_value() >= rhs.get_value();
}

bool operator==(const Fancy_Class& lhs, const Fancy_Class& rhs)
{
    return lhs.get_value() == rhs.get_value();
}

bool operator!=(const Fancy_Class& lhs, const Fancy_Class& rhs)
{
    return lhs.get_value() != rhs.get_value();
}

std::ostream& operator<<(std::ostream& os, const Fancy_Class& obj)
{
    return os << "Fancy_Class { value: "
              << obj.get_value()
              << ", name: "
              << obj.get_name()
              << " }";
}

int main(int, char**)
{
    std::vector<Fancy_Class> all_the_things = {
        {1, "thing1"},
        {3, "thing3"},
        {5, "thing5"}
    };

    Set<Fancy_Class> set(&all_the_things);

    size_t target = 6;
    Set<Fancy_Class> best_set = set.find_biggest_subset_le(target);

    std::cout << "Sum: " << best_set.get_sum() << std::endl;
    std::cout << best_set << std::endl;
}

Expected output:

Sum: 6
{
 Fancy_Class { value: 1, name: thing1 }
 Fancy_Class { value: 5, name: thing5 }
}

This is a useful review of operator overloading and template requirements. The template does not care that the elements are instances of Fancy_Class. It cares whether the required operations are available.

An Alternative: Implicit Conversion

Another possible approach is to define a conversion operator and let the object convert itself to a numeric type when needed. That can be convenient, though it can also make code behavior less explicit.

class Fancy_Class
{
private:
    size_t _value;
    std::string _name;

public:
    Fancy_Class(size_t value, std::string name) : _value(value), _name(name) {}

    size_t get_value() const { return _value; }
    std::string get_name() const { return _name; }

    operator size_t() const
    {
        return _value;
    }
};
Implicit conversions can reduce boilerplate, but they can also hide what the program is doing. They are convenient, but they should be used carefully.

If your Set<T> implementation is written with this sort of flexibility in mind, then this style may also work. It is a good example of how template design and operator design interact.

Takeaways

  • The user owns the original collection of elements.
  • A Set<T> object can act as a solver for the subset sum problem.
  • The returned answer can also be represented as a Set<T> object.
  • Generic code works only when the element type supports the operations the template expects.

If this page raises more questions than it answers, that is useful too. It usually means you are starting to see how template requirements, class design, and user-facing APIs fit together.
